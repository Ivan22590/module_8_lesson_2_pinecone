# Telegram-бот с LLM: сравнение ботов «с памятью» и «без памяти»

Учебный проект (урок «память»): три Telegram-бота, общающихся с нейросетью через
[ProxyAPI](https://api.proxyapi.ru/) (OpenAI-совместимый провайдер). Главная цель —
на живом примере показать, **что даёт боту память** и как меняется его поведение.

| | Без памяти | С памятью (SQLite) | С памятью (Pinecone, RAG) |
|---|---|---|---|
| Файл | `bot_without_memory.py` | `bot_with_memory.py` + `database.py` | `bot_pinecone_memory.py` + `pine.py` |
| Хранение долгосрочной памяти | ❌ Нет | ✅ SQLite: все тезисы подряд | ✅ Pinecone: векторный поиск |
| Что попадает в промпт | — | Все тезисы пользователя | Топ-10 релевантных смыслу запроса |

---

## Структура проекта

```
.
├── bot_without_memory.py    # Бот без памяти: каждый запрос обрабатывается независимо
├── bot_with_memory.py       # Бот с памятью: история диалога + тезисы в SQLite
├── database.py              # Слой долговременной памяти (SQLite) для бота с памятью
├── bot_pinecone_memory.py   # Бот с векторной памятью (Pinecone, RAG-поиск топ-10)
├── pine.py                  # Клиент Pinecone: upsert/fetch/query/delete + get_embedding
├── test.py                  # Демо: наполнение индекса «lesson» 20 фактами про Nissan и Volkswagen
├── .env.example             # Шаблон переменных окружения
├── requirements.txt         # Зависимости
└── .venv/                   # Виртуальное окружение Python
```

## Установка и запуск

```bash
# 1. Виртуальное окружение и зависимости
python -m venv .venv
.venv\Scripts\activate        # Windows (в Linux/macOS: source .venv/bin/activate)
pip install -r requirements.txt

# 2. Переменные окружения
copy .env.example .env        # Windows (в Linux/macOS: cp .env.example .env)
# Откройте .env и заполните TG_BOT_API_KEY, PROXYAPI_API_KEY и PINECONE_API_KEY

# 3. Запуск одного из ботов
python bot_without_memory.py   # бот без памяти
python bot_with_memory.py      # бот с памятью (SQLite)
python bot_pinecone_memory.py  # бот с векторной памятью (Pinecone, RAG)
```

> Для `bot_pinecone_memory.py` нужен индекс Pinecone — он создаётся автоматически
> при первом запуске (имя по умолчанию `bot-memory`, serverless, размерность 1536).

## Как работает каждый бот

### Бот без памяти (`bot_without_memory.py`)

Каждое сообщение — отдельный, независимый запрос:

```
[system prompt] + [текущее сообщение]  →  LLM  →  текст ответа
```

- Никаких предыдущих сообщений модель не видит — «чистый лист» на каждое сообщение.
- Ответ модели (простая Markdown-разметка) конвертируется в HTML Telegram;
  длинные ответы нарезаются на части ≤ 4096 символов с сохранением разметки.
- Индикатор «печатает…» поддерживается всё время ожидания ответа.

### Бот с памятью (`bot_with_memory.py` + `database.py`)

Работает **три уровня контекста** одновременно:

1. **Краткая история** — последние `HISTORY_LIMIT` (по умолчанию 20) сообщений
   диалога хранятся в оперативной памяти (`deque` per-chat) и передаются в запрос.
2. **Долгосрочная память** — после каждого ответа модель выделяет ключевые
   **тезисы** диалога, которые сохраняются в SQLite-базу (таблица `user_<id>`).
   Перед следующим запросом все сохранённые тезисы подгружаются в системный
   промпт. База переживает перезапуски: бот помнит интересы пользователя хоть
   через неделю, хоть через год.
3. **Структурированный вывод** — модель возвращает не свободный текст, а
   JSON-объект с двумя ключами (см. раздел ниже).

```
[system prompt + тезисы из БД] + [история] + [текущее сообщение]
        →  LLM (structured output)  →  {"theses": [...], "message": "..."}
                                              │               │
                                       сохраняется в БД   в чат пользователю
```

Команды бота:

- `/start` — приветствие;
- `/clear` — **полная очистка памяти**: краткая история диалога + таблица
  тезисов пользователя в БД. После очистки бот начинает помнить всё заново.

### Бот с векторной памятью (`bot_pinecone_memory.py` + `pine.py`)

Третий вариант: долгосрочная память хранится в векторной базе
[Pinecone](https://www.pinecone.io/), а перед каждым ответом выполняется
**семантический поиск** — в промпт попадают не все тезисы подряд, а только
**топ-10 релевантных** текущему вопросу (RAG-подход). При росте памяти бот
не «тонет» в нерелевантных фактах.

```
сообщение пользователя
   → get_embedding()                     эмбеддинг вопроса (text-embedding-3-small)
   → Pinecone query(top_k=10)            фильтр по user_id: чужую память не видим
   → системный промпт + top-10 релевантных воспоминаний
   → LLM (structured output)             {"theses": [...], "message": "..."}
        │               │
  ответ в чат     новые тезисы → get_embedding → upsert в Pinecone
```

- **Изоляция пользователей:** `user_id` хранится в metadata каждого вектора,
  поиск всегда идёт с фильтром `{"user_id": {"$eq": ...}}`.
- **Без дубликатов:** id вектора строится из md5-хеша текста тезиса
  (`user_<id>_<hash>`) — повторный тезис перезаписывает старый, а не создаёт копию.
- **Асинхронность:** синхронный `PineconeClient` обёрнут в `asyncio.to_thread`,
  чтобы не блокировать event loop aiogram.
- **Индекс создаётся сам:** при первом запуске `pine.py` создаёт serverless-индекс
  (по умолчанию `bot-memory`, dimension 1536, метрика cosine).

Команды бота:

- `/start` — приветствие и описание возможностей;
- `/clear` — полная очистка: краткая история + все воспоминания пользователя
  удаляются из Pinecone (`delete_by_filter` по user_id);
- `/stats` — сколько воспоминаний хранится о пользователе в векторной базе.

## Демонстрационное наполнение (`test.py`, `pine.py`)

**`pine.py`** — самостоятельный клиент векторной базы:

- `PineconeClient(index_name, dimension, ...)` — подключение, автосоздание индекса;
- `upsert(vectors)` — запись/обновление векторов пакетами по 100
  (кортежи `(id, values)` или `(id, values, metadata)`);
- `fetch(ids)` — чтение векторов по идентификаторам;
- `query(vector, top_k, filter, ...)` — поиск ближайших соседей
  с фильтром по metadata и namespace;
- `delete_by_ids` / `delete_by_filter` / `delete_all` — удаление;
- `describe_index_stats()` / `list_ids(prefix)` — статистика и перечисление векторов;
- `get_embedding(text)` — эмбеддинг текста через ProxyAPI
  (модель `openai/text-embedding-3-small`, 1536 размерностей).

**`test.py`** — демо-наполнение индекса `lesson`: 20 фраз про автомобили
Nissan и Volkswagen «Жук» (10 + 10 фактов). Каждая фраза превращается
в эмбеддинг и записывается в индекс: `id` — порядковый номер фразы,
metadata — сам текст. После заливки выводится статистика индекса.

```bash
python test.py   # создаст индекс «lesson» и зальёт 20 векторов
```

## ⭐ Сравнение двух ботов

### С какой из них проще работать

| Критерий | `bot_without_memory` | `bot_with_memory` | `bot_pinecone_memory` |
|---|---|---|---|
| Файлов | 1 модуль | 2 модуля (`+database.py`) | 2 модуля (`+pine.py`) |
| Концепций | Конфиг, LLM-запрос, отправка | + история, тезисы, SQLite, structured output | + эмбеддинги, векторный поиск, RAG |
| Зависимости | aiogram, openai, dotenv | + pydantic, sqlite3 (stdlib) | + pydantic, pinecone, dotenv |
| Настройка | Минимальная | Нужна БД (файл `memory.db` создаётся сам) | Нужен ключ Pinecone (индекс создаётся сам) |
| Долгосрочная память | Нет | Все тезисы пользователя в SQLite | Топ-10 релевантных смыслу запроса из Pinecone |
| Стоимость запросов | Дешевле: короткий промпт | Чуть дороже: промпт растёт с тезисами и историей | Промпт всегда умеренный: только релевантные тезисы |
| Диалог с человеком | «Амнезия» на каждом сообщении | Живой непрерывный диалог с «ячейкой памяти» | Диалог + «выборочная память»: вспомнит то, что относится к вопросу |

**Вывод:** для старта и понимания механики проще бот **без памяти** — один файл,
минимум кода, ничего лишнего. Бот **с памятью** сложнее (больше кода, больше
концепций, нужна БД), но именно он превращает «болталку» в осмысленный диалог
и демонстрирует реальную механику ассистентов вроде ChatGPT-памяти. Бот
**с Pinecone** добавляет к этому семантический поиск: память масштабируется
без разрастания промпта, а в контекст попадают только факты, релевантные
текущему вопросу — это рабочий паттерн production-ассистентов (RAG).

### Как память меняет реакцию бота на команды и запросы

Пример диалога без памяти:

> **Пользователь:** Какая погода в Сочи?
> **Бот:** В Сочи сейчас +25, ясно…
> **Пользователь:** А завтра?
> **Бот:** ❓ Уточните, о чём речь — я не вижу предыдущих сообщений.

Тот же диалог с памятью:

> **Пользователь:** Какая погода в Сочи?
> **Бот:** В Сочи сейчас +25, ясно… *(в БД сохранено: «Пользователь хочет
> поехать в Сочи»)*
> **Пользователь:** А завтра?
> **Бот:** Завтра в Сочи ожидается +27 и без дождей — отличный день для
> прогулки! *(контекст «Сочи» взят из истории)*

А через неделю:

> **Пользователь:** Привет! Подскажи, чемодан брать большой или маленький?
> **Бот:** Учитывая, что вы планировали поездку в Сочи, для недельного отдыха
> достаточно среднего чемодана… *(тезис из БД подтянулся автоматически)*

### Как меняется поведение модели при накоплении истории

- **Непрерывность мысли:** местоимения («он», «там», «завтра»), сокращения и
  отсылки к прошлым репликам понимаются корректно — модель видит последние
  `HISTORY_LIMIT` сообщений.
- **Персонализация:** тезисы из БД добавляются в системный промпт с пометкой
  «долгосрочная память о пользователе» — модель опирается на прошлые интересы,
  меньше переспрашивает, может уточнять детали («вы упоминали, что едете в Сочи…»).
- **Накопление:** каждый ответ приносит новые тезисы; дубликаты отбрасываются
  (уникальный индекс в таблице), поэтому память не раздувается от повторов.
- **Ограничение:** краткая история обрезается по размеру (`deque(maxlen=...)`) —
  в запрос всегда попадает только окно последних сообщений, а долгосрочные
  тезисы хранятся целиком.

### Как меняется поведение после очистки (`/clear`)

- Краткая история диалога удаляется из памяти процесса.
- Таблица `user_<id>` удаляется из БД — все накопленные тезисы стираются безвозвратно.
- Дальше бот отвечает «с чистого листа»: не помнит ни прошлых тем, ни интересов.
- При этом бот полностью работоспособен и начинает накапливать память заново
  с первого же нового сообщения.

> Сравните сами: поговорите с `bot_with_memory.py`, попросите `/clear`, задайте
> тот же вопрос — и заметите разницу в ответах.

## Формат тезисов и структурированный вывод

Бот с памятью использует **встроенный структурированный вывод** openai —
`client.chat.completions.parse(..., response_format=BotReply)`. API сам генерирует
JSON-schema из Pydantic-модели и валидирует ответ; при неподдержке провайдером
предусмотрен ручной разбор JSON (fallback).

Pydantic-модель ответа:

```python
class BotReply(BaseModel):
    theses: list[str]  # тезисы диалога для БД (пользователь их не видит)
    message: str       # сообщение для чата — отправляется человеку
```

Пример ответа модели:

```json
{
  "theses": [
    "Пользователь хочет поехать в Сочи",
    "Пользователь хочет купить чемодан",
    "Саша хочет узнать цены на перелёт"
  ],
  "message": "Для поездки в Сочи достаточно среднего чемодана…"
}
```

- `message` → уходит в чат как обычная реплика бота (с разметкой Telegram).
- `theses` → сохраняются в БД и в следующий раз подставляются в системный промпт.

## База данных (`database.py`)

- Движок: **SQLite** (файл `memory.db` рядом со скриптом, путь настраивается
  через `MEMORY_DB_PATH`). Режим WAL, запросы выполняются в отдельном потоке,
  чтобы не блокировать event loop.
- Схема:
  - `users` — каталог всех известных пользователей;
  - `user_<id>` — таблица конкретного пользователя:
    `id`, `thesis TEXT UNIQUE`, `created_at`.
- Имя таблицы строится только из проверенного целого id — SQL-инъекция через
  идентификатор пользователя невозможна.
- Дубликаты тезисов отбрасываются (`INSERT OR IGNORE` + уникальный индекс).
- `/clear` выполняет `DROP TABLE user_<id>` — полное стирание памяти пользователя.
